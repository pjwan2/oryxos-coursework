# Design decisions

Short records of the choices that shape the code, with the alternative that was not taken and what it costs. Most were made in the stage that introduced them; the stage is given so the longer account in [course-progress.md](../course-progress.md) can be found. "Open" means the decision still needs a human.

| ID | Decision | Why | Cost / what was not done | Stage |
|---|---|---|---|---|
| D-01 | **Keep the nine course modules** and dependencies pointing at `core`. | Matches the course layout; makes R1 to R11 in [module-boundaries.md](module-boundaries.md) checkable. | Some classes sit where the lesson put them rather than where they would be ideal (see the two known deviations there). | A |
| D-02 | **The core owns contracts, not implementations.** It imports only the JDK. | A Spring Boot upgrade, a different database or a different model library cannot reach the orchestration logic. | More small interfaces (`AgentSessionStore`, `ToolCallAudit`, `ToolCallHistory`, `ProfileCatalog`...) and test fakes for them. | A to B4 |
| D-03 | **One orchestrator, three entrances.** CLI, REST and the scheduler all call `AgentService.process(channel, userId, profile, message)`. | One place to enforce Profile lookup, session handling, cleanup of `ProfileContext`, persistence on failure. | The identity of the caller is only a string triple, not an authenticated principal. | A, B3, B4 |
| D-03a | **Session id is deterministic** `channel:userId:profile`, built by `SessionIds`, validated against `[A-Za-z0-9_-]{1,64}` per part. | The same conversation is reachable from any entrance; no id table; restart-safe. | A session cannot have two parallel threads; concurrent writers to the same id can overwrite each other (known limitation). | A |
| D-04 | **Provider does not execute tools.** `ProviderService` sends tool schemas and sets `internalToolExecutionEnabled(false)`; the ReAct loop asks `AgentToolExecutor` to run them. | Permission checks and audit must be ours, not the model library's. | We carry our own mapping between Spring AI messages and the session transcript. | A |
| D-05 | **Every tool call goes through `AuditedToolExecutor`**, including refusals. | A refused action is exactly what a reviewer wants to see. | One DB write per call; audit failures are logged but do not change the tool's result. | A, B2 |
| D-06 | **Sandbox rights are the intersection** of what the Profile declares (`settings.sandbox`) and the operator ceiling (`oryxos.sandbox.*`); no declaration means deny everything. Passed explicitly in `ToolContext`, no thread-local. | An agent cannot grant itself more than the operator allows, and agents cannot see each other's rights. | Writing a Profile takes more effort. The check is an application-level policy, not OS isolation. | B2 |
| D-07 | **Invalid security configuration stops startup**; other invalid profiles are skipped. | A skipped sandbox declaration would run an agent with different rights than its author believes. | One bad sandbox section blocks the whole application. | B2 |
| D-08 | **A second `AgentService` bean exists for the lesson 17 lab** (`lesson17AgentService`, scripted model). | Lesson 17's tests and the `/labs/payment` endpoint predate the Spring AI gateway and must keep working. It shares the session store, the audited executor and the registry. | A reader can mistake it for a second system. It is `@Primary`, so code that wants the real engine must ask for `springAiAgentService` by name; `AgentInvoker`, `BootCliRuntime` and `SchedulerConfiguration` do. Removing the lab is a candidate cleanup. | A |
| D-09 | **Memory is one interface with three backends** (`LongTermMemoryStore`: Markdown, SQLite, Mem0), chosen by `oryxos.memory.backend`; the same abstract contract test runs against each. | The course asks for pluggable memory; the contract keeps behaviour identical. | The contract is the lowest common denominator (keyword substring search, no semantic search). | B1 |
| D-10 | **CORE memory is always in the prompt, ARCHIVAL is searched and truncated**; the model must opt in by having a memory tool in its Profile. | Facts that must never be lost vs. notes that can be recalled on demand. | The model can write CORE itself; there is no human approval step (open). | B1 |
| D-11 | **No automatic fact extraction from conversations**; memory is written only by an explicit `save_memory` call. | Predictable, auditable; no hidden writes. | Less "magic" than hosted memory products. | B1 |
| D-12 | **Migrations are our own small versioned runner** (`schema_migrations`, SHA-256 checksums, backup + rehearsal on a copy), not Flyway. | The course project had no migration tool and one-file SQLite; a new library was not requested. | Less tooling than Flyway; no down-migrations; backups are never auto-deleted. | B3 |
| D-13 | **Scheduler: in-process, single-instance.** Spring `TaskScheduler` with `CronTrigger(cron, zone)`, a per-task single-flight lock, runs recorded in SQLite. | The course scope (lesson 25/28); no coordination service. | Two instances on one database fire twice. Missed runs during downtime are not replayed. | B3 |
| D-14 | **Manual run ignores `enabled`**, cron does not. | A person pressing "run" means it. The UI says so before it runs. | Needs an explicit warning in every client. | B3, B4 |
| D-15 | **"Run succeeded" means the agent run did not throw.** A sandbox refusal is a successful run with a denied audit row. | Keeps the technical status simple; the audit has the detail. | Needs UIs and reports to show both facts. The admin console does (see [web-service-design.md](../coursework/week04/web-service-design.md)). Whether a refusal should count as failure is open. | B3, B4 |
| D-16 | **REST controllers are thin**; running an agent is `AgentInvoker`, which validates input and translates errors, and nothing else. | R5; error semantics live in one place. | An extra class between controller and service. | B4 |
| D-17 | **Fixed error texts**: 500 is always `Internal server error`; provider and exception messages are never returned; provider failures are classified (`ModelFailures`) into 503 and 504 and then stripped of their text. | Provider messages can contain keys and URLs. | Debugging needs the server log (with `X-Trace-Id`). | A, B4 |
| D-18 | **Management API is local-only, not authenticated.** Server binds `127.0.0.1`; sensitive endpoints require loopback peer, no forwarding headers, local `Origin`, local `Host`. | There is no authentication in the course scope, and the console must not become an open door. | Any process or user on the machine can still call it. Must be replaced by real authentication before any exposure (open). | B3, B4 |
| D-19 | **Admin console: Vue 3 + Vite, built into the JAR, no second server.** SPA fallback only under `/admin/`. | One deployable, same origin (no CORS). | The build needs Node; the web module refuses to build without the console output. | B4 |
| D-20 | **The console shows technical status and tool audit separately** and never presents a refusal as success. | D-15. | Tool audit is matched by session and time window (no execution id column). | B4 |
| D-21 | **Schema is owned by storage** (`db/schema.sql` + migrations); Hibernate `ddl-auto: none`. | One source of truth, upgradable old files. | The two paths (fresh file, upgraded file) must agree; `SqliteMigrationTest` compares them table by table. | B3 |
| D-22 | **Static checks stay on and block the build** (Spotless, Checkstyle, PMD, SpotBugs at Max effort / Medium threshold); findings are fixed in code. | Quality gate that does not erode. | Several rounds adapted code to analyser heuristics (for example the session store method is called `discard`, because SpotBugs treats `delete*` as a mutator). | A to B4 |
| D-23 | **Architecture rules are tests** (`ArchitectureRulesTest`). | Boundaries that are only written down drift. | Text scanning, not bytecode analysis; it checks imports and the pom, not runtime wiring. | Week 4 delivery |

## Open decisions (need a human)

1. Should a model be allowed to write CORE memory without approval? (D-10)
2. Should a sandbox refusal inside a scheduled run mark the run as failed? (D-15)
3. Should memory be per agent instead of global? The course text for this was not available.
4. When authentication is added, which principal replaces the `userId` string in the session id? (D-03a, D-18)
5. Remove the lesson 17 lab bean and `ReActLabMain` once nothing depends on them? (D-08)
